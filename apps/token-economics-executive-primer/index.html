1 The 60-second version
If you read nothing else.

AI language models charge by the token — a token is a small chunk of text, roughly ¾ of a word. You pay for the tokens that go in (your question plus everything the system feeds the model alongside it) and the tokens that come out (the model's answer). Prices are quoted per million tokens, and output is typically 3–6× more expensive than input.

The single most important idea: the published price per million tokens is rarely what decides your bill. What decides it is how many tokens each interaction consumes — and that is an architecture and design choice, not a price-list choice. The same business task can cost 1× or 50× depending on how it's built.

So the executive question is never just "which model is cheapest?" It is "how much text are we sending through the model, how often, and do we actually need all of it?" This primer builds that intuition from the ground up.

🚕
Mental model — a metered taxi. The price per mile (the model's token price) matters, but your fare is driven by how far you go and how often you ride (tokens per interaction × number of interactions). A cheap per-mile rate on a route 10× longer than necessary is still an expensive trip.
2 What is a token? (try it)
The unit you are billed in — made tangible.

Models don't read whole words; they read tokens. A token is a fragment of text: common short words ("the", "is") are one token each, while longer or rarer words get split into pieces. A useful rule of thumb in English:

1 token ≈ 4 characters ≈ ¾ of a word.  →  1,000 tokens ≈ 750 words ≈ a page and a half of an email.  →  1 million tokens ≈ a 1,500-page book.

3 How you actually pay
Input vs. output, the price list, and a worked example.

3.1 Two meters running at once

Every model call has two charges:

  • Input (prompt) tokens — everything you send to the model: the user's question, plus instructions, plus any documents or history you attach. Cheaper per token.
  • Output (completion) tokens — everything the model writes back. More expensive, often 3–6×, because generating text is more compute-intensive than reading it.

3.3 A worked example — one customer question

A support assistant answers one customer. It reads: a 500-token instruction ("you are a helpful agent, follow these rules…"), 2,000 tokens of retrieved help-centre articles, the customer's 80-token question. It writes a 300-token reply.
Input = 500 + 2,000 + 80 = 2,580 tokens → 2,580 ÷ 1,000,000 × $3.00 = $0.0077
Output = 300 tokens → 300 ÷ 1,000,000 × $15.00 = $0.0045
Total ≈ $0.012 per answer — about one cent.

One cent feels free. But run it 2 million times a month (a mid-size contact centre) and it's ~$24,000/month, ~$290k/year — for a single use case, on a premium model, before any people or infrastructure cost. Now the design choices that move that one-cent figure up or down by 5× really matter.

Watch-out: notice the customer's actual question was only 80 of the 2,580 input tokens — 3%. The other 97% is "scaffolding" the system adds (instructions + retrieved documents). This is almost always where the cost — and the savings — live.

5 How architecture changes the bill
Six design levers — each shown as a before/after on the same task.

These are the decisions that actually set your cost. Each one is an engineering choice with a direct price tag. Use them as the vocabulary for the conversation with your technical team.

Lever 1 — How much context you stuff in (RAG)

To answer about your business, a model needs your data fed in alongside the question — this is "retrieval-augmented generation" (RAG). Feed it the 5 most relevant paragraphs or the entire 40-page policy? Both work; one costs 10× more on every single call.

Before: attach whole document, 8,000 input tokens → $0.024/call input.   After: retrieve top 5 chunks, 1,000 tokens → $0.003/call.  → 8× cheaper, often better answers (less noise to distract the model).

Lever 2 — How much conversation history you replay

Models have no memory between calls. To "remember" a chat, the app re-sends the whole conversation every turn. By turn 20, you may be paying to re-read 19 previous turns on every message. Options: send a rolling window, or send a short summary instead of the full transcript.

Before: replay full 4,000-token history each turn.   After: replay a 400-token running summary.  → ~10× cheaper on the history portion, with minor quality trade-off.

Lever 3 — One call vs. an agentic loop

An agent doesn't answer in one shot — it loops: reason → act → observe → repeat. Each lap is a paid call, and because it re-reads the accumulating context, later laps are the most expensive. A 5-step agent can cost 5–8× a single call for the same question. Often worth it for complex work — but a choice to make deliberately, not by default.

A frequent waste: using an 8-step research agent for a question a single RAG lookup could answer. Match the machinery to the job.

Lever 4 — Which model you point at the task

From Section 3.2, frontier is ~50× budget on input. Using a frontier model to classify "is this email a complaint? yes/no" is like couriering a postcard. Reserve premium/frontier for the genuinely hard 10–20% of calls.

Lever 5 — Prompt caching

The instruction block and reference documents are often identical on every call. Caching lets the provider store that repeated chunk and charge a steep discount (often ~75–90% off) when it reappears. For a support bot with a fixed 500-token instruction hit 2M times a month, this is close to free money — but only if engineering turns it on.

Before: 2,580 input tokens at full price.   After: 2,500 of them cached at ~90% off → you pay full price for ~80 tokens.  → input cost cut by ~85%.

Lever 6 — Smart routing

Instead of sending every query to one model, a router first judges difficulty and sends easy queries to the budget tier, hard ones to premium. A typical 70 / 20 / 10 blend (budget / mid / premium) can cut token cost 50–70% versus "premium for everything," with no quality loss on the easy majority.

Stacking them. These levers compound. Tight RAG × summarised history × caching × routing on the support example can take that ~$0.012/answer down toward ~$0.002 — a ~6× reduction on an otherwise identical user experience. That's the difference between a $290k and a $50k annual line item.

7 How to think about it
Five mental models to carry into any AI cost conversation.
  1. Cost = tokens-per-interaction × interactions × price. Three dials, not one. Engineering controls the first, the business controls the second, the vendor sets the third. Most leverage is in the first.
  2. The user's words are the small part. The expensive tokens are the instructions, retrieved documents and replayed history the system adds. Ask: "what are we sending that the model doesn't strictly need?"
  3. Output is the premium meter. Output tokens cost 3–6× input. Concise, structured responses are cheaper and usually more useful. "Write me a 5-page essay" is a cost decision.
  4. Match the engine to the job. Most enterprise queries are easy. Defaulting everything to the most powerful model is the most common and most expensive mistake.
  5. Unit economics scale, mistakes scale faster. A one-cent inefficiency is invisible in a pilot and a six-figure problem at production volume. Get the per-interaction design right before you scale, not after.
The reframe for clients: token price is a procurement question; tokens-per-interaction is an architecture question — and that's where 5–50× cost differences are won or lost. The cheapest model badly architected loses to a premium model well architected.
8 How to act on it
A practical checklist — questions to ask and levers to pull.

Questions to ask your team (no jargon required)

  • "How many tokens does one interaction use, and what's in them?" If nobody can answer, that's the first finding.
  • "How much of what we send the model is the user, vs. instructions and documents?" Anything >90% scaffolding is a savings target.
  • "Are we using one model for everything?" If yes, ask what a routed tier would save.
  • "Is prompt caching turned on for the repeated parts?" Often a one-line change for a large saving.
  • "Does this task really need an agent loop, or would a single retrieval call do?"
  • "What's our cost per interaction, and how does it scale to full volume?" Always reason in unit economics.

On procurement (price, not architecture)

  • Volume discounts typically open up at $1M+ annual spend — negotiate, don't accept list price at scale.
  • Prices fall fast — roughly 40–50% per year for equivalent capability. Avoid long lock-ins that assume today's prices.
  • Batch / off-peak tiers exist for non-urgent work (often ~50% off) — use them for back-office jobs that don't need a real-time answer.
9 One-page cheat sheet
Print this. Carry it into the meeting.

The vocabulary

  • Token — ~¾ of a word; the billing unit.
  • Input tokens — what you send in (cheaper).
  • Output tokens — what comes back (3–6× pricier).
  • Context window — max tokens a model reads at once.
  • RAG — feeding your documents in alongside the question.
  • Prompt caching — discount on repeated input.
  • Smart routing — easy → cheap model, hard → premium.
  • Agent loop — multiple paid calls per interaction.

The numbers worth memorising

  • 1,000 tokens ≈ 750 words ≈ 1½ pages.
  • Budget tier is ~50× cheaper than frontier.
  • Output costs ~3–6× input.
  • Caching: ~75–90% off repeated chunks.
  • Routing: ~50–70% off vs. premium-for-everything.
  • An agent can cost 5–50× a single call.
  • List prices drop ~40–50% per year.
If you remember one sentence: "Our AI cost is set less by the price per token than by how many tokens each interaction uses — and that's a design choice we control."
